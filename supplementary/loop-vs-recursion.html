Loop vs. RecursionSupplementary

Chapter 4 taught you one way to repeat something: a loop. Chapter 6 quietly opened a second one — a function is allowed to call itself. This topic runs a real iterative program and a real recursive program that compute the exact same answer side by side, so you can watch, statement by statement, what each one is actually doing underneath: one mutates a couple of variables in place, the other builds a real stack of pending calls — the same call stack from S7.

01 · The idea

Two mechanisms, one job: making something happen more than once

S10.1The anatomy of a recursive function

Every correct recursive function needs exactly two parts: a base case that stops the recursion outright, and a recursive case that does a small piece of work and then calls itself on a smaller version of the same problem. Side by side with the loop that does the same job:

factorial — iterative
int factLoop(int n) {
    int result = 1;
    for (int i = 1; i <= n; i++)
        result = result * i;
    return result;
}
factorial — recursive
int factRec(int n) {
    if (n <= 1)          // base case — stops it
        return 1;
    return n * factRec(n - 1);  // recursive case — smaller n
}

Both compute 5! = 120. The loop counts up from 1, multiplying as it goes. The recursive version does the opposite: it keeps deferring the actual multiplication (“I'll give you the answer once I know factRec(n-1)”) until it hits n <= 1, and then all those deferred multiplications resolve on the way back out.

S10.2What a recursive call actually costs

Recall S7: every function call — recursive or not — pushes a real stack frame holding its own parameters and locals. A loop reuses the same frame and the same few variables for every pass; recursion keeps every pending call's frame alive, stacked underneath the one currently running, until it returns. Measured for real by this page's own lab:

sum 1..5factorial(5)
Loop — variables in use, ever3 (n, i, total) — constant3 (n, i, result) — constant
Recursion — peak stack depth7 frames6 frames

That gap only widens as the input grows: a loop summing 1..1,000,000 still uses 3 variables; the matching recursion would try to stack up roughly a million frames. This is exactly why C++ programs really do run out of stack memory on deep, large-input recursion — a cost a loop simply never pays.

S10.3Same bug, two different failures

A loop with a broken condition and a recursive function with an unreachable base case are the same mistake — “forgot to move toward stopping” — but they fail in genuinely different ways, both captured for real in the Lab's third preset:

Missing terminating step in…What actually happens
a loopkeeps looping forever in one frame — constant memory, just never stops (S5's infinite loop, from the other side)
a recursive functionkeeps calling itself, pushing a new frame every time, until it runs out of stack memory and crashes: "stack overflow"
A genuinely different failure mode An infinite loop hangs. Unterminated recursion crashes — and it usually crashes fast, because real stack memory is much smaller than the memory available for ordinary variables. Always ask: for this call, is the argument guaranteed to get closer to the base case?

S10.4Where recursion earns its keep

If recursion costs more memory, why use it? Sometimes the recursive version is simply the more honest translation of how the problem is already defined — and sometimes it does something a straightforward loop cannot do as directly. Move the print to after the recursive call instead of before it:

printAscending.cpp
void printAscending(int n) {
    if (n == 0) return;
    printAscending(n - 1);   // go all the way down FIRST
    cout << n << " ";      // then print, on the way back OUT
}
// printAscending(5) prints: 1 2 3 4 5

Nothing here reversed anything by hand: the calls dive down to n == 0 first, and the cout lines execute in the exact reverse order the calls were made — for free, using the call stack itself as the "storage" that remembers what still needs printing. A loop can do this too, but only by first storing the values somewhere (an array, Chapter 5) and then printing that storage backwards.

Short-Circuit EvaluationSupplementary

Chapter 3 mentioned it in one paragraph: && and || stop evaluating as soon as the answer is certain. This topic takes that one sentence seriously — because it means C++ genuinely never calls some of the code you wrote, and that has consequences that go far beyond speed: it is how real programs guard against crashes, and how real bugs hide inside conditions that look perfectly innocent.

3 ideas Short-Circuit Lab mini-app 8-question quiz
01 · The idea

Evaluation stops the instant the answer is certain

S9.1Not "evaluates fast" — evaluates not at all

a && b only needs to check b when a is true — if a is false, the whole expression is already false, no matter what b is. a || b is the mirror image: only when a is false does b matter. C++ guarantees it will not waste time confirming what it already knows:

ExpressionLeft operand is…Right operand
a && bfalsenever evaluated — result is false
a && btrueevaluated — it decides the result
a || btruenever evaluated — result is true
a || bfalseevaluated — it decides the result

“Never evaluated” is a stronger claim than “doesn't matter”. If b is a function call, that function is not invoked. If it has a side effect — printing something, incrementing a counter, changing a variable — that side effect does not happen. This is guaranteed by the C++ standard, not an implementation detail a particular compiler happens to choose.

S9.2The guard pattern — order is a safety decision

The single most useful consequence is the guard pattern: put the check that makes an operation safe before the operation itself, in the same && chain.

safe_guard.cpp
// idx might be out of range — check FIRST
if (idx >= 0 && idx < n && arr[idx] > 0) {
    cout << "positive";
}

When idx is -1, idx >= 0 is false, the chain stops right there, and arr[idx] — the dangerous part — is never reached. Now swap the order:

unsafe_guard.cpp — do not do this
// arr[idx] runs FIRST — before idx is checked at all
if (arr[idx] > 0 && idx >= 0 && idx < n) {
    cout << "positive";
}
This is not a style preference C++ evaluates && and || strictly left to right — the compiler is not allowed to reorder the terms for you, not even if reordering them would be safer. arr[idx] in the second version runs with an out-of-range idx and reads memory it has no business touching: undefined behaviour — it might crash, might not, might return garbage. Writing the bounds check first is what actually prevents this, and it only works because of short-circuit evaluation.

S9.3Where the bug hides: skipped side effects

The same rule that makes the guard pattern safe can silently break code that expects both sides of a condition to run:

hidden_side_effect.cpp
if (hasCache() || computeExpensive()) {
    cout << "ready";
}
// if hasCache() is true, computeExpensive() NEVER runs —
// including whatever it was supposed to update along the way

Nothing here is a compiler bug — this is short-circuit evaluation working exactly as specified. The mistake is assuming a condition's right-hand side "always runs anyway". Whenever a term inside && / || does more than answer true or false — a function call, an i++, an assignment — ask first: is this term guaranteed to be reached?

02 · Mini app

Short-Circuit Lab — watch each term actually get called, or not

Five real conditions, each a chain of terms joined by one operator. Press Step and watch the call log fill in one term at a time — the moment the result is certain, every remaining term turns grey and is marked never called: it genuinely did not run.

Things to try Compare the first two presets: identical terms, different order, one of them safe. Step through the OR permission chain and notice it stops the moment any role matches. Finally look at “the worst case” — an && chain that happens to be true all the way through: nothing is skipped, and the full cost of all four checks is paid. Short-circuiting saves work sometimes, not always.

From Source Code to Running ProgramSupplementary

You press “compile and run” — and a plain text file somehow becomes a process the CPU executes. This topic walks that journey step by step: preprocessor, compiler, assembler, linker, loader. Then it opens the hood of this website's Playground, which takes a completely different route: an interpreter that never produces machine code at all.

01 · The build pipeline

Five steps from hello.cpp to “Hello world!”

S1.1The whole journey at a glance

Each stage is a separate program. Each one consumes the previous stage's output — your source file gradually turns into something the processor can execute.

Nothing on this page is invented Every file name, line count, byte, and terminal line below was produced by actually running a real compiler on a real hello.cpp while writing this page (Apple Clang, invoked as g++ — MinGW/GCC on Windows or Linux will differ in small details, never in the pipeline itself). Nothing is hand-typed to look plausible; you can reproduce every one of these steps yourself.

S1.2Step 1 — the preprocessor, on a real file

You met it in Chapter 2: the preprocessor runs before the compiler. When it sees #include <iostream>, it pastes the entire contents of that file into yours. Here is the real, complete source file used for this demo:

hello.cpp — 7 lines, the whole file
#include <iostream>
using namespace std;

int main() {
    cout << "Hello world!" << endl;
    return 0;
}

Running g++ -E hello.cpp -o hello.i stops the pipeline right after the preprocessor and saves its output. The real result: 59,350 lines from a 7-line file — the compiler's own headers pull in the C++ standard library's internal implementation. The very top shows exactly which files got pasted in, and where:

hello.i — real first lines (of 59,350)
# 1 "hello.cpp"
# 1 "<built-in>" 1
# 1 "hello.cpp" 2
# 1 ".../c++/v1/iostream" 1 3
# 1 ".../c++/v1/__config" 1 3
# 1 ".../c++/v1/__config_site" 1 3

Those # line "file" markers are not your code — they are bookkeeping the preprocessor leaves behind so that later, if the compiler finds an error, it can still report your file and line number even though everything now lives in one enormous pasted-together text (a total of 3,671 such file-entry markers, real count, for this one #include). Scroll all 59,350 lines down and your own three statements are still there, byte for byte, completely unchanged, right at the very end:

hello.i — real last lines
using namespace std;

int main() {
    cout << "Hello world!" << endl;
    return 0;
}

This whole pasted-together text is the translation unit — what the compiler actually reads next.

S1.3Steps 2 & 3 — compiler and assembler, on a real file

The compiler does the intelligent work: it checks your syntax and translates C++ into assembly language — human-readable names for the processor's own instructions. The assembler then converts that listing into raw binary machine code, stored in an object file. The full hello.i compiles to hundreds of lines of assembly (name-mangled library calls and all), so this demo uses a second, tiny real file to keep the output readable:

ret0.cpp — 3 lines, the whole file
int main() {
    return 0;
}

g++ -S ret0.cpp -o ret0.s really produced this — nothing trimmed, nothing rewritten by hand:

ret0.s — real compiler output
main:                    # @main
        xorl    %eax, %eax
        retq

Notice the compiler did not write mov eax, 0 — it chose xorl %eax, %eax (“XOR the register with itself”) instead, a genuine micro-optimization real compilers make because it is a shorter instruction than loading the constant 0. Then g++ -c ret0.cpp -o ret0.o assembles that listing into a real object file, and disassembling it (objdump -d ret0.o) shows the exact bytes the assembler chose for each instruction:

ret0.o — real objdump -d output
0000000000000000 <main>:
   0: 31 c0    xorl    %eax, %eax
   2: c3       retq

Three bytes, total — 31 c0 c3 — is the entire machine-code body of this function. The object file that holds them opens with its own real signature, too: hex-dumping ret0.o shows it starts with the bytes 7f 45 4c 46, which spelled out as ASCII characters read .ELF — the four-byte magic number every Linux/Unix object file and executable begins with, so the OS can recognise the format before touching anything else in the file.

Compile-time errors A missing semicolon or an undeclared variable is caught in step 2 — before anything runs. If the compiler objects, no executable is produced at all.

S1.4Step 4 — the linker, on a real file

Your object file is not complete: it uses cout, but the code that actually paints characters on the screen lives in the C++ standard library, compiled long ago by someone else. Go back to the real hello.o from step S1.2 and list its symbols (nm hello.o) and one really is left unresolved, marked U for “undefined”:

nm hello.o — real output, one line
                 U __ZNSt3__14coutE

That cryptic name is real too — it is std::cout after name mangling, the scheme C++ compilers use to encode a symbol's namespace and type into one linker-safe identifier. Now really link it — g++ hello.o -o hello — and ask the finished executable what it depends on (otool -L hello on macOS; the equivalent on Linux is ldd hello):

otool -L hello — real output
hello:
        /usr/lib/libc++.1.dylib
        /usr/lib/libSystem.B.dylib

libc++ is exactly “the code that lives in the C++ standard library” — the linker recorded a real dependency on it, and the undefined cout symbol from before is gone. If it cannot find something — say a function is declared but never defined — linking really fails. Compiling and linking a file that calls an undefined helper(int) produces this genuine error:

g++ badref.o -o badref — real error
Undefined symbols for architecture arm64:
  "helper(int)", referenced from:
      _main in badref.o
ld: symbol(s) not found for architecture arm64

On GCC/MinGW (the toolchain most Windows labs use) the identical failure is worded undefined reference to `helper(int)' — different wording, same real cause: the linker went looking for that symbol's machine code and it was nowhere to be found.

S1.5Step 5 — loading and running, for real

When you run ./hello, the operating system copies the executable into memory and points the CPU at its first instruction. From there the processor executes machine instructions one after another — exactly the flow of control you drew in Chapter 1's flowcharts. This is the real, unedited transcript of running the hello built above:

terminal — real session
$ ./hello
Hello world!
$ echo $?
0

One more real number: hello.o is 10,416 bytes, but the finished, linked hello is 38,856 bytes — bigger, but nowhere near the size of the whole standard library, because the linker recorded dependencies on libc++ and libSystem (step S1.4) rather than copying them in wholesale. Errors that depend on actual values — dividing by a zero the user typed, reading past the end of an array — only appear now, at run time.

ErrorCaught atBy
missing semicolon, unknown variablecompile timecompiler (step 2)
declared but never defined functionlink timelinker (step 4)
division by zero, index out of boundsrun timethe running program (step 5)
02 · A different route entirely

How the Playground's interpreter is different

S1.6No machine code, ever

The Playground (and every exercise box on the chapter pages) does not compile your program. It runs MiniCPP, an interpreter written in JavaScript that lives inside this very web page. Its pipeline stops long before machine code:

When the evaluator meets x = x + 1, no processor instruction for that addition is ever generated — the interpreter (a JavaScript program) looks up x in its variable table, adds one, and stores it back. It is the same idea as the Flowchart Studio's step-runner in Chapter 1, just for real C++ syntax.

S1.7Compiler vs interpreter, side by side

Compiled (g++, clang)Interpreted (the Playground)
Translationwhole program → machine code, before runningnone — the source is executed as it is read
What executes your codethe CPU, directlyanother program (the interpreter)
Speedfast — native instructionsslower — every step goes through the interpreter
Syntax errorsall reported up front, at compile timereported when the source is parsed, before any statement runs
Distributionship the executable; source stays privatethe source itself is what you share and run
Setupneeds a compiler toolchain installednothing to install — it is already in this page
Why the Playground chose this route Real C++ is a compiled language — that is what you will use in labs. The Playground trades raw speed for instant, installation-free feedback, plus safety nets a compiler cannot give: it counts every step, so an infinite loop is stopped and reported instead of freezing your browser, and an out-of-bounds array index becomes a clear error message instead of silent memory corruption.
Not either/or Many modern languages mix the two ideas: Python interprets a compiled bytecode; Java compiles to bytecode and then compiles the hot parts to machine code while running (JIT). Compilation vs interpretation is a spectrum, and the C++-to-executable pipeline above sits at one well-defined end.

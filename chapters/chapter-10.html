Databases

Every app you use is a thin layer on top of a database. This chapter follows the textbook from files to tables: data and information, keys and foreign keys, the SQL language for asking questions and defining tables, and then the syllabus’s big question — what a query actually does, and how to make it faster. You will write real queries in a small SQL engine and watch it count the rows it has to read, with and without an index.

10.1Data, information, and the database that holds them

Data are raw facts: the numbers 8.5, 7.0 and 9.0, the text “SV20260002”, a date of birth, a photo of a student card. On their own they mean very little. Information is data that has been processed and organised until it helps someone decide something: “Student SV20260002 has an average of 8.17 and is in the Good band”, or “Class X has 40 students and a class average of 7.85”.

CriterionDataInformation
NatureRaw, unprocessedProcessed, meaningful
MeaningOften unclear on its ownSupports decisions
Example8.5, 7.0, 9.0Course average: 8.17
PurposeThe input, the raw materialThe output, the useful result
FormCan be scattered and messyStructured and easy to read

A database is the machinery in the middle: an organised collection of logically related data, stored once, that many users and applications can search, update and share at the same time. The lecture's one-line version: structured data engineered for fast searching, safe updating and concurrent access. Besides the data itself, a database has three properties the textbook stresses:

  • Self-describing. It stores metadata — the names, types and rules of every table — in a system catalogue, so the data can be understood without any particular program.
  • Data abstraction. Programs ask for data by name; where and how it is laid out on disk is the database's business. Change the storage and the programs hardly notice.
  • Multiple views. Each user or application sees only the part of the data it needs, which also helps security.

You meet databases every day: university and school systems, banking, online shopping, hospitals, inventory and sales, social media, library catalogues, airline reservations.

From your C++ programs An array from Chapter 5 lives in memory and is gone when the program ends, and only that one program can see it. A database is the program-independent memory: it outlives every program that uses it, and many programs can use it together.

10.2Why not just files? Databases and the DBMS

Before databases, every application kept its own files (.txt, .csv, .xlsx…) in its own layout. The textbook's example is a university where the Training Department and the Student Affairs office each keep files that repeat student ID and name. Five problems follow:

ProblemWhat it looks like in the university
Separation and isolationTo list students with GPA below 2.0 who live in the dormitory, someone must join files of two departments by hand, with a one-off program.
Duplication → inconsistencyA student changes phone number; only Student Affairs is told. Now two departments hold two different numbers.
Data dependenceThe field layout lives inside each program. Widening “Address” from 50 to 100 characters means converting the file and editing every program that reads it.
Incompatible formatsTwo departments, two languages or tools, two file formats: sharing becomes a project.
Fixed queriesUsers cannot ask new questions themselves; every new report needs a programmer, so the number of programs explodes.

The lecture lists the same weaknesses as four short phrases: files mean high redundancy, single-user access, weak security, and are easy to break; a database system means reduced redundancy, concurrent access, built-in security and integrity constraints. Both lists have two root causes: the definition of the data is buried inside the programs, and nothing central controls access.

The fix has two parts that are easy to confuse. The database is the data (plus its metadata). The DBMS (Database Management System) is the software that defines, creates, maintains and controls access to it: MySQL, PostgreSQL, Oracle and SQL Server are DBMSs. Together they form the database system. A DBMS lets you:

  • describe the structure of the data, and add, change, delete and query it conveniently;
  • control who may see or change what;
  • manage transactions so data stays consistent and correct;
  • back up and recover after a failure;
  • let many users work at once without clashing.
AdvantagesDisadvantages
DataLess duplication, so less storage and fewer out-of-sync copies; one shared copyMigrating from old files takes time and effort
ProgramsData independence: change the structure without rewriting every applicationA more complex system that needs a database administrator (DBA)
UseConcurrent users, faster retrieval, better security, recovery after a crashHigher start-up cost (software, hardware, training); a poor design can be slow at large scale

10.3A short history: from files to tables to the cloud

Each era of data management fixed the pain of the one before. Reading the right column of this table is a good way to remember why the next model was invented.

EraWhat appearedThe pain it solved or created
1960sIsolated file systems, then the first two database models: hierarchical (a strict parent-child tree; IBM’s IMS) and network (a flexible web, many parents per child)Redundancy, inconsistency, no sharing. The new models were rigid or hard to navigate: programmers had to know physical pointers, so changing storage broke programs.
1970The relational model: E. F. Codd of IBM publishes it. Data lives in tables and rests on mathematicsPrograms no longer depend on how data is stored. Query languages such as SQL grow out of it.
1980sRelational databases become the commercial standard; SQL standardisedThe foundation of Oracle, MySQL, PostgreSQL and SQL Server.
1980–2000Object-oriented, distributed and multimedia databases; then the web: Oracle, SQL Server and MySQL spread through businessThe Internet creates demand to connect databases to web applications.
2000s onBig data, social media and cloud computing: NoSQL (“not only SQL”) systems for huge, flexible, distributed data (concept 10.9)Relational systems struggled to scale out across many servers; NoSQL trades strict structure for scale and flexibility.
TodayLearned indexes, vector databases, serverless and lakehouse designs (concept 10.9)Intelligence and elasticity in the data layer.
Did you know? One of the very first database systems was built to count rocket parts. IBM began developing IMS, a hierarchical database, in 1966 to keep track of the bill of materials for the Saturn V rocket of the Apollo programme; the first version ran on an IBM System/360 and was installed in 1968. IMS is still in use in large organisations today. Source: Wikipedia — IBM Information Management System.

Future users of large data banks must be protected from having to know how the data is organized in the machine (the internal representation).

E. F. Codd, opening sentence of the abstract of “A Relational Model of Data for Large Shared Data Banks”, Communications of the ACM 13(6), June 1970 — the idea of data independence, in one line.
Slides corrected The lecture slides place the hierarchical and network models in the “1970s” and the NoSQL pivot in the “2010s”. The textbook dates the first two to the 1960s (IMS began in 1966), Codd’s relational paper to 1970, and the NoSQL wave to the 2000s onward; the 2010s is when it went mainstream. This page uses the textbook’s dates.

10.4The relational model: tables, keys, and promises

In the relational model a database is a set of tables (formally relations). Each table has named columns (attributes) and holds rows (tuples); each row describes one real-world thing or one relationship; each cell holds one value. Think of the C++ you already write:

student.cpp — a row, and a table
struct Student {            // one ROW
    int    id;                // columns...
    string name;
    int    year;
    double gpa;
};
Student students[10];         // the whole TABLE: an array of rows
student_idnameyeargpa
211001An13.5
211002Binh23.8

The same two records as a table: the table is the array, a row is one struct, a column is one member, a cell is one value.

Everyday wordFormal wordMeaning
TableRelationA named, two-dimensional collection of rows
Row / recordTupleOne entity, for example one student
Column headerAttributeA property; every value in the column has the same type
SchemaRelation schema R(A1, …, An)The table’s name and column list; the number of columns is its degree

The model comes with rules: table names are unique; each column has a name and is found by name, not by position; the order of rows has no meaning; no two rows are identical; every cell holds a single atomic value (a student with two phone numbers needs a separate table, not a list in one cell); and NULL marks a value that is missing or unknown.

Keys: how a row is found

A superkey is any set of columns that never has the same values in two rows; all the columns together always qualify. A key (candidate key) is a minimal superkey: drop any column and uniqueness is lost. In the textbook's STUDENT table, {SSN} is a key, while {SSN, Name, Age} is a superkey but not a key (SSN alone already does the job). A table may have several candidate keys; the designer picks one as the primary key (preferably the shortest) and the others become unique keys.

The slide's rule of thumb: a primary key must be unique and never NULL. Good: Student ID. Bad: email (people change it) and name (two students can share one: the sample data has two Binhs). A good key is stable, unique, and means nothing else.

Entity integrity is exactly that rule: a primary-key value may not be NULL, so every row can be found. Try the “bad primary key” example in the lab below to watch a database refuse a second Binh.

student_idnameemail
211002Binhbinh@uni.edu
211005Binhbinh2@uni.edu

Same name, different people. name cannot be the key; student_id can.

Foreign keys: how tables connect

A foreign key is a column (or set of columns) whose values must match the primary key of a row in another table, or be NULL if unknown. It enforces referential integrity: you cannot enrol student 999999 if no such student exists. When a parent row is deleted or changed, the database can refuse it (RESTRICT, the default), delete the dependent rows too (CASCADE), or set them to NULL (SET NULL).

Slides corrected The slide’s COURSES table contains a Student_ID column, so CS102 appears twice with different students: Course_ID is not unique, so it cannot be a key, and the “one-to-many” label is wrong, because a student takes many courses and a course has many students. That is a many-to-many relationship, and the standard cure is a third table (here enrolments) that holds one row per (student, course) pair. The slide also names student 2 “Binh” on one page and “Bob” on the next; the lab data uses Binh.

Beyond keys, the model has domain constraints (a GPA must be a number from 0 to 10), semantic constraints (business rules such as “no employee may work more than 40 hours a week on all projects”) and transition constraints (“a salary may only go up”). The last two cannot be drawn on a schema, so they are written in the design documents and enforced by code.

10.5SQL: asking the database a question

SQL (Structured Query Language) is the standard language for relational databases. It is declarative: you describe what you want, and the DBMS decides how to get it. SQL commands fall into three groups:

GroupPurposeCommands
DDL — Data DefinitionCreate and manage the structureCREATE, ALTER, DROP
DML — Data ManipulationRead and change the rowsSELECT, INSERT, UPDATE, DELETE
DCL — Data ControlPermissions and securityGRANT, REVOKE
Did you know? SQL started life with a longer name, SEQUEL (Structured English Query Language), designed at IBM in the 1970s by Donald Chamberlin and Raymond Boyce after they learned about Codd’s relational model. It was shortened to SQL (dropping the vowels) because “SEQUEL” was already a trademark of a UK aircraft company, Hawker Siddeley Dynamics Engineering. Source: Wikipedia — SQL (history).
Slide corrected The lecture slide calls SQL “a data manipulation language, not a general programming language”. The second half is fair (you do not write loops and functions the C++ way), but SQL is more than DML: it also defines structure (DDL) and controls access (DCL). The textbook’s three-group split above is the complete picture.

SELECT: the shape of a query

Every question you ask is a SELECT; its result is itself a table. Only SELECT and FROM are required; the clauses must be written in this order:

ClauseWhat it does
SELECTwhich columns or expressions to show
FROMwhich table (or tables) to read
WHEREkeep only the rows that satisfy a condition
GROUP BYgather rows with the same value into groups (concept 10.6)
HAVINGkeep only the groups that satisfy a condition
ORDER BYsort the result, ASC (default) or DESC

Notice the trap: you write SELECT first, but the DBMS runs the clauses in this order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. That is why a column alias created in SELECT can be used in ORDER BY but not in WHERE: when WHERE runs, the alias does not exist yet.

SELECT Fname, Lname, Salary FROM Employee;           -- only the columns you name

SELECT DISTINCT Salary FROM Employee;                -- 6 different salaries, each shown once

Changing the data

students.sql — INSERT, UPDATE, DELETE
INSERT INTO students VALUES (211011, 'Lan', 2, 3.2, 'lan@uni.edu', 'Hue');
UPDATE students SET gpa = 3.4 WHERE student_id = 211011;

INSERT adds a row, UPDATE changes the rows that match its WHERE, DELETE removes them. Constraints (concept 10.7) are checked every time: a statement that would break a rule is refused, and nothing changes.

10.6Summaries, groups and sub-queries

Often you want one number about many rows. SQL has five aggregate functions, each turning a column into a single value:

FunctionReturnsNotes
COUNTnumber of rowsCOUNT(*) counts every row; COUNT(col) skips NULLs
SUMtotal of a columnnumbers only
AVGmean of a columnnumbers only
MIN, MAXsmallest, largestwork on text and dates too

Every aggregate except COUNT(*) ignores NULLs. In the lab's university data, one student has no GPA, so COUNT(*) gives 10 but COUNT(gpa) gives 9. Put DISTINCT inside (COUNT(DISTINCT Dno)) to count each value once. Aggregates may appear only in the SELECT list and in HAVING; and a query with an aggregate but no GROUP BY may select nothing else, which is why SELECT SSN, COUNT(Salary) FROM EMPLOYEE is an error (which SSN would it show?).

aggregates.sql — textbook examples 3.11 to 3.14
SELECT COUNT(*) AS Employees FROM EMPLOYEE;                      -- 8
SELECT COUNT(DISTINCT Dno) AS Departments FROM EMPLOYEE;         -- 3
SELECT COUNT(SSN), SUM(Salary) FROM EMPLOYEE WHERE Dno = 5;      -- 4 and 133000
SELECT MIN(Salary), MAX(Salary), AVG(Salary) FROM EMPLOYEE;      -- 25000, 55000, 35125

GROUP BY and HAVING

Sub-queries: a question inside a question

A sub-query is a SELECT inside another statement, usually in WHERE or HAVING. A scalar sub-query returns one value (one row, one column) and can sit next to = or >; one that returns a column of values is used with IN. Sub-queries are how you get around the “no aggregates in WHERE” rule.

subqueries.sql — examples 3.17 to 3.19
-- 3.17: a sub-query that returns ONE value
SELECT Fname, Lname, Salary
FROM EMPLOYEE
WHERE Dno = (SELECT Dnumber FROM DEPARTMENT WHERE Dname = 'Research');

-- 3.18: WHERE Salary > AVG(Salary) is illegal, so compute the average in a sub-query
SELECT Fname, Lname, Salary,
       Salary - (SELECT AVG(Salary) FROM EMPLOYEE) AS SalDiff
FROM EMPLOYEE
WHERE Salary > (SELECT AVG(Salary) FROM EMPLOYEE);

-- 3.19: sub-queries nested three deep, run from the inside out
SELECT DISTINCT Fname, Lname
FROM EMPLOYEE
WHERE SSN IN (SELECT Essn FROM WORKS_ON
              WHERE Pno IN (SELECT Pnumber FROM PROJECT
                            WHERE Plocation = 'Houston'));

Example 3.17 returns the four Research employees (John Smith, Franklin Wong, Ramesh Narayan, Joyce English). Example 3.18 computes the average salary, 35 125, and returns the four people above it. For Example 3.19, the innermost query finds the Houston projects, the middle one finds who works on them, and the outer one fetches names.

10.7Defining tables: CREATE TABLE, types and constraints

Design check A constraint is a promise the database keeps for every program. Rules in C++ code (if (gpa > 10) …) protect one program; a CHECK protects the data from all of them. When you design the library or canteen database in the team activity, write down which promise each constraint keeps.

10.8Indexes: how a query finds its rows fast

When you ask for WHERE Lname = 'Smith', how does the DBMS find the matching rows? With no help, it reads every row and checks each one: a full table scan, whose cost grows in direct proportion to the size of the table. An index is an extra structure that avoids that, exactly like the index at the back of a book: instead of reading every page for “binary search”, you look the word up in an alphabetical list and jump to the right pages. In a DBMS the index stores the values of one column (the indexing field) in sorted order, each with a pointer to the row that holds it. The search happens in the small index; the pointers lead straight to the data.

Index typeDefinition (textbook)SQL Server name
Primary indexOn the primary-key (unique) field; the rows are physically sorted by itClustered
Clustering indexOn a non-key field (values may repeat); rows are still physically sorted by itClustered
Secondary indexOn any column; does not change the physical order; a table can have manyNonclustered

A table can have only one primary or clustering index, because its rows can only be stored in one physical order. In the lab, a primary key or a UNIQUE column gets an index automatically; CREATE INDEX adds a secondary one on any other column (one column per index in the lab).

example_3_24_25.sql — create and drop an index
-- 3.24: no index on Lname: the DBMS must read every row (full table scan)
SELECT Fname, Lname, Salary FROM EMPLOYEE WHERE Lname = 'Smith';

-- 3.25: build an index, run the SAME query: look in the (small, sorted) index first,
--        then follow the pointers straight to the matching rows
CREATE INDEX idx_employee_lname ON EMPLOYEE (Lname);

DROP INDEX idx_employee_lname;       -- remove it again

Counting the work: binary search, the one you already wrote

“Sorted, so jump to the middle and discard half” is the binary search you may have met with arrays in Chapter 5. It is what an index does. Take a sorted list of 15 ids and look for 68. A linear scan checks entries from the front and needs 10 comparisons; binary search needs 3.

binary_search.cpp — your Chapter 5 code, with a step counter
int binarySearch(const int a[], int n, int target, int &steps) {
    int low = 0, high = n - 1;
    steps = 0;
    while (low <= high) {
        int mid = (low + high) / 2;
        steps++;                          // one comparison
        if (a[mid] == target) return mid;
        if (a[mid] < target) low = mid + 1;   // target is in the upper half
        else                 high = mid - 1;  // target is in the lower half
    }
    return -1;                            // not there
}

int main() {
    int ids[15] = {3, 8, 15, 21, 27, 34, 42, 51, 60, 68, 75, 83, 90, 94, 99};
    int steps;
    int pos = binarySearch(ids, 15, 68, steps);
    cout << "68 found at index " << pos << " after " << steps << " comparisons\n";
    // prints: 68 found at index 9 after 3 comparisons
}

Read the table from the top and three lessons fall out:

  • Selective lookups win big. Finding 19 rows out of 2 000 drops from 2 000 to 50. A join is the same lookup repeated for every row of the other table, so an index on the join column turns 200 100 into 5 298.
  • An index helps only when the query can use it. It is sorted by the column’s value, so it answers =, <, >, BETWEEN and IN. It says nothing about words that end in “ho”, and a column hidden inside arithmetic (customer_id + 0) is no longer the sorted value.
  • When most rows match, the index does not pay. The last day range matches half the table, and the index route (2 025) is even a little worse than reading everything (2 000).
A real index is smarter than the lab’s A production DBMS keeps statistics and chooses between a scan and an index for you, and some systems can use an index for a pattern like LIKE 'Pho%' (a fixed beginning). The lab’s planner is deliberately simple so every number is explainable. The idea carries over: count the rows you must touch.

Why a B-tree, not just a sorted array? Supplementary

A plain sorted array searches fast but is slow to change: inserting one value means shifting everything after it. Real DBMSs therefore keep the sorted order in a B-tree (the textbook mentions its B⁺-tree variant). A B-tree generalises the binary search tree by letting each node hold many keys and have many children, which keeps the tree very shallow and puts the data in few separate disk blocks. That is why the textbook’s 200 000-row table needed only 3 reads: three levels of the tree. Binary search on a sorted array is the right mental model; the tree is how it stays fast while rows come and go. Source: Wikipedia — B-tree.

The price, and what to index

Index helpsIndex costs
Look-ups and ranges on the indexed column; joins on it; sometimes sortingExtra storage for the sorted entries
Reads that touch a few rows out of manyEvery INSERT, UPDATE or DELETE must also fix the index: the lab prints “N index entries had to be updated”
Tables that are read far more than they are writtenWasted space and slower writes if no query ever filters on that column

Rule of thumb: index the columns your queries filter and join on, especially when each value matches few rows; skip columns that are rarely searched or that have only a few distinct values; remember that writes get slower. Primary keys are indexed for you; a foreign key such as orders.customer_id is not, and is usually the first candidate.

10.9NoSQL, and where databases are heading

By the 2000s, companies such as Google, Amazon, Facebook and Twitter were storing billions of user records, posts, logs and sensor readings, with very high read and write rates. Classic relational systems struggled to scale out (add more servers instead of buying a bigger one), to handle data whose structure keeps changing, and to stay fast for millions of concurrent users. NoSQL (“not only SQL”) systems answered by putting scale, speed and availability first and giving up some strictness. Typical traits:

  • Flexible schema: records describe themselves; adding a field needs no table redesign.
  • Horizontal scalability: grow by adding servers to a cluster.
  • Eventual consistency: copies of the data agree after a short while, instead of the instant, strong consistency of ACID transactions.
  • Sharding and replication: data is split across nodes and copied for speed and fault tolerance.

Chapter 8 · Computing Track · Week 44

Assembly & Compilers

The processor understands only numbers; you write while loops. This chapter bridges the gap: machine language, the readable assembly language that sits one-to-one on top of it, and the compiler, assembler and linker that turn your C++ into something the CPU can run. You will watch a real compiler's output, then build a tiny compiler of your own and run what it produces on last week's machine.

01 · Learn the concepts

From C++ down to bits — and back up again

The lecture slides cover machine language and the toy instruction set (concepts 8.1–8.3) but have no dedicated slides on compilers. The compiler material (8.5–8.7) therefore comes from the textbook (§1.6–1.8) and the supplementary topics, and is marked Supplementary where it goes beyond both.

8.1Machine language: the only language the CPU speaks

A machine-language instruction is one binary word: an opcode that says what to do plus address fields that say on which cells (last week's 7.9). The CPU can execute nothing else. The slides' example: set A = B + C, where the variables A, B, C live in memory cells 100, 150 and 151. In the toy language of slide 34 that is three instructions:

StepInstructionWhat it does
1LOAD 150R ← CON(150), that is B
2ADD 151R ← R + CON(151), that is B + C
3STORE 100CON(100) ← R, that is A

The slide notes an alternative: a machine with a three-address ADD 150, 151, 100 would do it in one instruction. More work per instruction, more circuitry — the RISC/CISC trade-off of 7.9 in miniature. On the lecture's 16-cell machine the same program is the numbers 0000 0110 · 0011 0111 · 0001 0101 (LOAD 6, ADD 7, STORE 5), which is what you see in the memory table of last week's lab. Nobody wants to write programs as bit strings — and nobody has to.

Slide note The slides write these instructions “English-like, should be binary”. The numbers 100, 150 and 151 are arbitrary choices of the slide; in the 16-cell lab, A, B and C sit right after the code.

8.2Assembly language and the assembler

Assembly language is machine language in a readable costume. Binary opcodes are replaced by mnemonics (LOAD, ADD) and numeric addresses by symbolic labels and names (B, total). It still maps almost one-to-one onto machine instructions, and so it depends completely on the processor: x86 assembly is not ARM assembly. The program that translates it into binary is the assembler. (Some assemblers add macros and pseudo-instructions, so the mapping is not always strictly one-to-one — the lab's assembler turns JUMPGE into two real jumps.)

a_equals_b_plus_c.asm — toy assembly (slide 28, textbook §1.6.1)
; A = B + C
        LOAD   B        ; R <- B
        ADD    C        ; R <- R + C
        STORE  A        ; A <- R
        HALT            ; end of program
.data
A:  0
B:  5
C:  7

The assembler's work is mechanical: look each mnemonic up in the opcode table, replace each name by the address of its cell, and write the resulting words into memory. .data (and, in many real assemblers, .text) are directives: they are not instructions, they tell the assembler how to lay out the program.

Did you know? Assembly is not a museum piece. The flight software of the Apollo Guidance Computer, which helped land people on the Moon, was written in AGC assembly language; the software team at MIT was directed by Margaret Hamilton, and the listings she is standing next to in this photo are software that she and her team produced. Today assembly survives in device drivers, firmware, boot code and interrupt handlers (textbook §1.6.1). Source: Wikipedia — Apollo Guidance Computer.

8.3Reading assembly: if and loops are compare-and-jump

There is no if, else or while in the instruction set — only COMPARE (which sets the condition codes) and JUMPs that either happen or do not. The textbook's example reads two integers and prints the larger one. A high-level if (a > b) cout << a; else cout << b; has to be broken into basic steps:

max.asm — if / else as compare + jump (runs in last week's lab)
        IN      A          ; cin >> a;
        IN      B          ; cin >> b;
        LOAD    A          ; R = a
        COMPARE B          ; LT = 1 when b < a, i.e. a is bigger
        JUMPLT  showA      ; if (a > b) go to the then-part
        OUT     B          ; else-part: cout << b;
        JUMP    done       ; skip the then-part
showA:  OUT     A          ; then-part: cout << a;
done:   HALT
Textbook correction The textbook's version of this program says JUMPGT “if A > B”. With slide 34's definition (COMPARE X sets GT when the content of X is greater than R), after LOAD A, COMPARE B the flag GT means B > A. The version above uses JUMPLT, which does mean A > B. Always check which operand a comparison puts first.

Loops use the same two ingredients with a jump backwards: run the body, compare, and jump up to the top again while the condition holds. Supplementary topic S5 — Loops are just jumps has the whole story with a “Jump Machine” you can step through; this chapter's lab compiles your own while loops to exactly this pattern. Conditions from Chapter 3 (if) and Chapter 4 (while) are therefore the C++ names for a compare and a jump.

8.4Programming at three levels

A program is an ordered list of instructions, each describing one basic action the hardware can do; the hardware itself does not know what “the program” is — it only fetches, decodes and executes. (Ada Lovelace saw as early as 1843 that Babbage's Analytical Engine could be given instructions on punched cards, which is why she is often called the first programmer.) Today the same computer can be programmed at three levels, each one giving up some control over the hardware in exchange for convenience:

LevelWhat it isExample
Machine codebinary instructions the CPU executes directly; format fixed by the ISAC7 45 FC 00 00 00 00 (x86-64)
Assemblymnemonics for machine instructions; almost one-to-onemovl $0, -4(%rbp)
High-level languagearchitecture-independent abstractions; one statement becomes many instructionsint sum = 0;

All three lines in the last column are the same action: put 0 into a variable. The compiler takes you from the bottom row to the top one's translation; the assembler from the middle row to the first.

8.5One program, three levels: real output from a real compilerSupplementary

The textbook (§1.8.2) takes “sum of 1 to 10” down all three levels. Here it is again, with output produced by actually running clang -S -O0 -fno-asynchronous-unwind-tables -target x86_64-apple-macos (Apple clang 21) on this function — nothing typed by hand except that assembler directives and comment lines were removed:

sum10.cpp — the C++
int sum10() {
    int sum = 0;
    for (int i = 1; i <= 10; i++)
        sum += i;
    return sum;
}
sum10.s — x86-64 assembly, clang -O0 (AT&T syntax)
__Z5sum10v:                       # the C++ name, "mangled" by the compiler
        pushq   %rbp
        movq    %rsp, %rbp
        movl    $0, -4(%rbp)            # sum = 0   (sum lives at rbp-4)
        movl    $1, -8(%rbp)            # i = 1     (i lives at rbp-8)
LBB0_1:
        cmpl    $10, -8(%rbp)           # compare i with 10
        jg      LBB0_4                  # if i > 10, leave the loop
        movl    -8(%rbp), %eax          # eax = i
        addl    -4(%rbp), %eax          # eax = eax + sum
        movl    %eax, -4(%rbp)          # sum = eax
        movl    -8(%rbp), %eax
        addl    $1, %eax
        movl    %eax, -8(%rbp)          # i = i + 1
        jmp     LBB0_1                  # back to the test
LBB0_4:
        movl    -4(%rbp), %eax          # the return value goes in eax
        popq    %rbp
        retq

The comments on the right were added by hand; the instructions are exactly what the compiler wrote. Compare it with your toy language: the same compare, conditional jump, back-jump — plus extra work (pushq, movq, memory for every variable) that the toy machine has no need for. Assembling it (clang -c, then otool -t) gives the actual machine code, 49 bytes in all. The first instruction, movl $0, -4(%rbp), is the seven bytes C7 45 FC 00 00 00 00: opcode C7, then 45 FC for “memory at rbp minus 4” (FC is −4), then the 32-bit constant 0. The whole function starts 55 48 89 e5 c7 45 fc 00 00 00 00 ….

Same function, two instruction sets

A simpler function, int add(int b, int c) { int a = b + c; return a; }, compiled for two real ISAs:

x86-64 (CISC) · clang -O0
        pushq   %rbp
        movq    %rsp, %rbp
        movl    %edi, -4(%rbp)
        movl    %esi, -8(%rbp)
        movl    -4(%rbp), %eax
        addl    -8(%rbp), %eax
        movl    %eax, -12(%rbp)
        movl    -12(%rbp), %eax
        popq    %rbp
        retq
ARM64 (RISC) · clang -O0
        sub     sp, sp, #16
        str     w0, [sp, #12]
        str     w1, [sp, #8]
        ldr     w8, [sp, #12]
        ldr     w9, [sp, #8]
        add     w8, w8, w9
        str     w8, [sp, #4]
        ldr     w0, [sp, #4]
        add     sp, sp, #16
        ret
x86-64 (CISC)ARM64 (RISC)
Machine code size24 bytes: 55 48 89 e5 89 7d fc 89 75 f8 8b 45 fc 03 45 f8 89 45 f4 8b 45 f4 5d c340 bytes: ten 4-byte words, e.g. d10043ff for sub sp, sp, #16
Instruction lengthvariable (1 to 3 bytes here)always 4 bytes
The additionaddl -8(%rbp), %eax reads memory directlyadd w8, w8, w9 only touches registers; ldr/str move data (load–store)

That is the RISC/CISC table of Chapter 7 in real code. Finally the same sum10 with optimisation on (-O2) — the textbook's constant-folding example, here from the real compiler:

sum10.s — clang -O2, x86-64
__Z5sum10v:
        pushq   %rbp
        movq    %rsp, %rbp
        movl    $55, %eax               # 1+2+...+10, computed by the COMPILER
        popq    %rbp
        retq

There is no loop at run time: the compiler understood the program and replaced it with its answer, 55 — eleven bytes of machine code instead of 49. A compiler is not just a translator.

8.6Who does what: compiler, assembler, linker, loaderSupplementary

“Compiling” a C++ program is really a small assembly line of separate programs. The textbook's review question 16 asks for the first two; the syllabus for this week lists compiling, linking and execution.

ToolReadsWritesIts role
CompilerC++ sourceassembly (or object code)checks syntax and types, chooses instructions, optimises; compile-time errors come from here
Assemblerassembly textobject file of machine codemechanical: mnemonics → opcodes, names → addresses
Linkerobject files + librariesexecutablejoins your code with library code (where cout lives) and fixes up addresses; “undefined reference” errors come from here
Loader (OS)executable filea running process in memorycopies the program into memory and sets the PC to its first instruction — then the fetch–decode–execute cycle takes over

The textbook's answer to question 16: the compiler translates a program in a high-level language into a lower-level form (assembly or machine code), and the assembler translates assembly text into binary machine code the CPU can execute. Because a compiler is itself just a program stored in memory (7.7), it can produce other programs as data. (Many compilers, including g++, call the preprocessor first and run the assembler for you.)

Did you know? Grace Hopper's A-0 system (1951–52), often named as the first compiler, did something closer to linking: a program was a list of subroutine numbers and arguments, and A-0 pasted the matching subroutines together into machine code. Modern compilers translate whole languages; the linking idea survived as its own tool. Source: Wikipedia — A-0 System.

8.7Inside a compiler: tokens, tree, instructionsSupplementary

A compiler's work falls into stages. Lexing cuts the text into tokens (while, (, i, <=, n …). Parsing arranges the tokens into a tree that captures the meaning (a while with a condition and a body); this is where a missing semicolon or an undeclared variable is reported. Code generation walks the tree and emits instructions; real compilers then optimise (like the folded 55 above). The assembler and linker follow.

The lab below is a complete miniature of that pipeline for a tiny language, aimed at last week's toy machine. Two things you will notice, both true for real compilers as well:

  • Names disappear. sum becomes cell number 8 or 9; the machine never sees the word.
  • A statement becomes several instructions. sum = sum + i; is LOAD sum, ADD i, STORE sum; a while is a test at the top, a jump at the bottom.

8.8Trade-offs: abstraction, control and performance

Why not write everything in machine code, or everything in Python? Because the levels trade three things against each other (textbook §1.8.3): how much abstraction you get, how much control you keep over the hardware, and how fast the result runs.

CriterionMachine codeAssemblyHigh-level language
Abstractionnonelowhigh
Control of the hardwarecompletecompletelimited
Portabilitynone (tied to the ISA)none (tied to the ISA)high, relatively
Readabilityvery lowlowhigh
Development speedvery slowslowfast
Run-time speedhigh if well writtenhigh if well writtendepends on compiler and runtime
Typical useboot firmwaredrivers, interrupt handlersapplications, systems

Table: textbook Table 1.5. Real systems mix levels. The Linux kernel is mostly C with small pieces of inline assembly where it must touch special registers; a game engine is C++ plus shader programs for the GPU; Python reaches good speed through libraries such as NumPy that are written in C/C++. And a good optimising compiler (GCC, LLVM/Clang) often matches or beats hand-written assembly — as the 55 above suggests. The question is never “which is best?” but “which balance fits this requirement?”. Where does C++ sit? It compiles to machine code in advance (this chapter), unlike the Playground's interpreter, which S1 contrasts.

02 · Lab

Tiny compiler

Pick one of the 26 example programs (basics, decisions, loops, classic algorithms, input processing, puzzles; each has a story, things to look for in the stages and challenges) or write your own C++: int, + − * / %, cin, cout, if / else if / else, while, for, do-while, break / continue and conditions joined with &&, || and !. Watch the program travel through the compiler's stages to the toy machine of Chapter 7, then open the assembly in last week's workbench with one button. This is a teaching compiler for a teaching machine: the target is the slide-34 instruction set, not x86 or ARM, and it only understands the subset listed under the editor. A real compiler's output looks like 8.5.

  • Your own code: the editor has line numbers and checks the program while you type. Every error names the line and column and gives a hint; unsupported C++ (text, double, arrays, functions) is rejected with a friendly message. Ctrl/Cmd + Enter compiles.
  • Keep it: your draft is saved automatically in this browser; My programs keeps named copies; you can download a .cpp file, open one, or copy a link that loads your program.
  • See the cost: the toy ISA has no multiply or divide, so *, / and % become loops of additions and subtractions that you can read on tab 3. The line being executed is highlighted in the editor while the CPU runs.
What this teaching compiler leaves out Real compilers keep variables in registers or on a stack, use immediate constants inside instructions (this ISA has none, so the constants 0 and 1 get memory cells of their own), reuse results and optimise. The toy machine's numbers are also unbounded, whereas a C++ int wraps around at 32 bits. And int x; starts at 0 here, but in real C++ it holds garbage until you assign it (the lab warns when you read such a variable). A real CPU has multiply and divide instructions; this one does not, so the lab writes loops for *, / and % (inline, or one shared routine when the program would not fit in the 256 cells). There is no stack either, hence no functions and no recursion here.

05 · Team activity

Language-level audit: which level for which job?

Teams of 3–4 · one class period to prepare · a 5-minute pitch. Counts toward the class-activities 10%.

The task

A start-up must build five pieces of software, and the team is the technical board. For each, decide the programming level (machine code, assembly, high-level language, or a mix), name the translation tools that will be involved, and defend the choice using the criteria of Table 1.5 (abstraction, hardware control, portability, readability, development speed, run-time speed).

Piece of softwareWhat is special about it
1 · The first code that runs when a small board powers onno operating system yet; must set up hardware registers
2 · A driver for a new network cardmust read and write device registers, and be fast
3 · The company's customer web applicationchanges weekly; many developers; runs on several machines
4 · The inner loop of a video encoderruns billions of times; every cycle counts
5 · A data-analysis script for the marketing teamused once; written by non-specialists

Constraints

  • For at least one piece, argue for a mix of levels and say exactly where the boundary lies.
  • For every piece, say who produces the machine code (compiler, assembler, interpreter, nobody) and what would go wrong if the machine changed from x86 to ARM.
  • One piece must be defended against the obvious answer: e.g. why not write the encoder loop in assembly by hand? (Hint: 8.5 and 8.8.)

Roles

RoleResponsibility
Criteria keeperscores each choice against the rows of Table 1.5
Toolchain engineernames the compiler, assembler, linker or interpreter in each case
Skepticattacks every choice with “what if the hardware changes?” and “what does this cost in developer time?”
Presenterpitches the five decisions in five minutes
Discussion starters Which of the five would you be most nervous to write in assembly, and why? If a compiler can match hand-written assembly, what is left that only assembly can do? What changes if the web application suddenly needs to be twice as fast?

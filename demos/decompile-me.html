Decompile Me

A detective game. Each case file holds the machine code of a hidden C++ program and a few sample runs. Write C++ that behaves the same. The tiny compiler translates your code, both programs run side by side on hidden test inputs, and the assembly of the two is compared line by line.

  1. Read the machine code and sample runs, and form a theory.
  2. Type your C++ (the tiny subset of Chapter 8's lab) and press Run on all tests.
  3. Watch the compiler stages light up, read the test grid and the assembly diff, then refine.
  4. Stars: 1 for the right behaviour, 2 for no more instructions than the target, 3 for the same instruction pattern.

Everything here is a simulation on the course's toy machine, not x86 or ARM. It runs entirely in your browser.

What am I looking at?

Exhibit A, the machine code. This is what the CPU of the toy machine actually receives (Chapter 8.1): every row is a memory cell holding a 4-bit opcode followed by an address, and the data cells hold the variables. With “Friendly labels” on, the page renames cell numbers to v1, v2, constants to k5 and jump targets to L1 (assembly language, 8.2). Turn it off to see the plain numbers.

No names, no structure. The original variable names, comments, braces and the words if and while are not in the machine code. An if becomes a COMPARE plus a conditional jump, a while becomes a jump backwards (8.3). That is why a decompiler can only guess, and why the last case has two different sources for the same machine words.

Compiler stages. The strip follows the pipeline of 8.7: your text is split into tokens, organised into a syntax tree, turned into assembly, assembled into machine code, and finally run by the fetch–decode–execute cycle of Chapter 7. A red stage is where the pipeline stopped. Click any stage to see what it produced.

Test grid. Programs are compared by behaviour on many inputs, not by reading the source. Passing the samples is not enough: the hidden tests exist because a compiler (or a teacher) must be right on inputs nobody tried.

Assembly diff. Two correct programs can compile to different instruction sequences, just as a different loop condition or an extra temporary changes the jumps (8.4, 8.8). The diff normalises names so that only the instruction pattern is compared. “Same instructions” (3 stars) is stricter than “same behaviour”.
